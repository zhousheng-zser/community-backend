# 前端对接说明：到家服务订单与九州派单

本文档面向 **小程序（用户端）**、**技工端**、**管理后台（Vue 九州运营端）** 对接开发，与当前后端实现一致。API 前缀统一为 **`/api/v1`**（若客户端 `baseUrl` 已含 `/api/v1`，则下列路径不再重复前缀）。

---

## 1. 通用约定

### 1.1 用户端 / 技工端 响应（到家订单相关控制器）

成功：

```json
{ "errno": 0, "data": { ... } }
```

失败（常见 HTTP 仍为 200，以 `errno` 判断）：

```json
{ "errno": 400, "errmsg": "说明文案" }
```

### 1.2 支付创建接口响应

`POST /service-orders/payments/create` 使用另一套字段（与集市支付对齐）：

成功：`{ "code": 0, "msg": "ok", "data": { ... } }`  
失败：`{ "code": <非0>, "msg": "..." }`（HTTP 多为 200）

### 1.3 鉴权

| 端 | Header |
|----|--------|
| 小程序用户 / 技工 | `Authorization: Bearer <登录 token>` |
| 管理后台 | `Authorization: Bearer <admin token>`（`adminAuthMiddleware`，登录见 `/api/v1/auth/admin/login`） |

## 2. 业务闭环（用户侧）

### 2.1 首页九宫格 / 分组服务

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| GET | `/core/service-groups/:key` | 可不登录 | `:key` 如 `urgent_fix`、`tidy` 等；返回分类与 `services[]`，用于落地页与选品 |
| GET | `/core/services/:id` | 可不登录 | 服务详情 |

用户从分组进入服务详情后 **下单不传 `worker_id`** 时，为 **平台派单路径**（支付后进入「待派单」，由九州指派同小区技工）。

### 2.2 创建服务订单（到家 SKU）

**`POST /service-orders`**（需用户 JWT）

请求体（常用字段）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `service_id` | number | 是 | 服务 ID |
| `community_id` | number | 否 | 小区 ID；不传则多用当前用户资料中的 `community_id` |
| `group_key` | string | 否 | 与首页分组一致，如 `urgent_fix`；未上架服务在允许的分组白名单内仍可下单 |
| `worker_id` | number | 否 | **直约**：传技工用户 ID；不传则为 **九州派单** |
| `address_id` | number | 否 | 用户地址表 ID |
| `address_snapshot` | object | 否\* | `{ label?, detail?, contact?, phone? }` 等；无地址时可与 `address`、`contact_name`、`contact_phone` 组合 |
| `appointment_time` | string | 否 | 预约时间 |
| `remark` | string | 否 | 备注 |
| `qty` | number | 否 | 数量，默认 1 |
| `goods_name` / `goods_price` | — | 否 | 展示与议价辅助 |

响应 `data` 示例：

```json
{
  "id": 1,
  "order_id": 1,
  "order_no": "SO17...",
  "status": "pending_pay",
  "pay_status": "unpaid"
}
```

**平台派单**（未传 `worker_id`）时，库内 `fulfillment_meta` 会包含：

- `await_user_confirm`: `true`
- `dispatch_mode`: `"admin_dispatch"`（前端可按需展示「平台派单」等文案）

**直约**（传 `worker_id`）时：

- 创单后 `status` 为 **`pending_worker_accept`**
- `fulfillment_meta` 含 `direct_worker: true`

### 2.3 支付

#### 方式 A：微信 JSAPI（推荐生产）

1. **`POST /service-orders/payments/create`**  
   - Body：`{ "order_no": "SO..." }`  
   - 返回 `data` 内 `wx_pay_params` / `jsapi` 等字段，用于 `wx.requestPayment`  
   - **注意**：当前实现要求订单 **`status === pending_pay` 且 `pay_status === unpaid`**。若直约单创单后为 `pending_worker_accept`，走微信预下单需与后端确认是否已放宽该校验；联调可先用方式 B。

2. 支付成功后以 **`GET /service-orders/payments/status?order_no=SO...`** 或拉 **`GET /service-orders/my`** 刷新状态。

#### 方式 B：Mock 支付（联调 / 部分环境）

**`POST /service-orders/:id/pay`**（需用户 JWT，`id` 为订单数字 id）

- 直接将 `pay_status` 置为 `paid`，并按规则推进 `status`（见 **第 4 节**）。

### 2.4 我的服务订单列表

**`GET /service-orders/my`**

Query：

| 参数 | 说明 |
|------|------|
| `page` | 页码，默认 1 |
| `limit` | 每页条数，默认 10 |

响应 `data`：

```json
{
  "list": [ /* 见下列表项 */ ],
  "total": 0,
  "page": 1,
  "limit": 10
}
```

列表项（节选，与 `serializeOrderRow` 一致）：

| 字段 | 说明 |
|------|------|
| `id` | 订单 id |
| `order_no` | 订单号 |
| `status` / `status_text` | 状态码与中文 |
| `pay_status` | `unpaid` / `paid` |
| `service_id` / `service_title` | 服务信息 |
| `amount` / `pay_amount` | 金额（字符串） |
| `community_id` / `group_key` | 小区与分组 |
| `worker_id` | 即 `assigned_worker_id`，未派单为 `null` |
| `fulfillment_meta` | 含 `dispatch_mode`、`direct_worker` 等 |
| `assigned_worker` | 已派单时 `{ id, nickname, avatar_url, worker_user_id }`，否则 `null` |

### 2.5 订单详情

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/service-orders/:id` | 路径参数为订单 **数字 id** |
| GET | `/service-orders/detail?order_no=SO...` | 按订单号查 |

详情在列表字段基础上可包含 `address_snapshot`、`service` 等（`withDetail`）。

### 2.6 用户确认服务完成

**`POST /service-orders/:id/confirm-complete`**（或兼容路径 `.../confirm`）

技工完工且订单处于待用户确认流程时，用户调用后进入 **`completed`**（以后端校验为准）。

## 3. 状态机（`status`，用户展示建议）

| status | 说明（后端 `status_text`） |
|--------|----------------------------|
| `pending_pay` | 待支付 |
| `pending_worker_accept` | 待技工接单（直约创单后；支付后仍可能维持此状态直至技工接单） |
| `paid_pending_dispatch` | **待派单**（已支付、等待九州指派技工） |
| `pending_accept` | 待服务商接单（服务商打包 / 绑定服务商的服务） |
| `dispatched` | 已派单（已指派技工，技工可接单履约） |
| `in_service` | 服务中 |
| `pending_user_confirm` | 待用户确认完成 |
| `completed` | 已完成 |
| `cancelled` | 已取消 |
| `closed` | 已关闭 |

**用户侧「九宫格下单 → 不配技工」典型路径：**

`pending_pay` →（支付）→ `paid_pending_dispatch` →（九州派单）→ `dispatched` → … → `completed`。

---

## 4. 支付成功后状态规则（便于联调对表）

在 `pending_pay` 或 `pending_worker_accept` 下支付成功时：

1. 若有 **`provider_user_id`（服务商）** → `pending_accept`
2. 否则若有 **`assigned_worker_id` 且 `fulfillment_meta.direct_worker`**（直约）→ **`pending_worker_accept`**
3. 否则若有 **`assigned_worker_id` 且无直约标记** → `dispatched`
4. 否则 → **`paid_pending_dispatch`**（待九州派单）

微信回调、虚拟支付、`mockPay` 与上述规则对齐。

## 5. 九州中台（管理后台）派单

运营后台菜单：**「九州派单（到家+帮帮）」**，路由 **`/home-service-dispatch`**，页面实现见仓库 **`admin/src/views/HomeServiceDispatch.vue`**。

### 5.1 待派单队列（聚合）

**`GET /admin/dispatch-queue`**（管理员 JWT）

返回示例结构（节选）：

```json
{
  "errno": 0,
  "data": {
    "service_orders": [ /* ServiceOrder 列表，含 service、buyer 等 */ ],
    "neighbor_assist_orders": [ /* 帮帮单 */ ]
  }
}
```

前端只关心 **`data.service_orders` 中 `status === paid_pending_dispatch` 且 `assigned_worker_id` 为空** 的到家单。

### 5.2 服务订单列表（可选）

**`GET /admin/service-orders`**

Query：`status`、`community_id`、`limit` 等，返回数组（每条含 `service`、`buyer`、`assignedWorker` 等）。

### 5.3 可派单技工列表（派单下拉）

**`GET /admin/housekeeping/workers`**

Query：

| 参数 | 说明 |
|------|------|
| `community_id` | **推荐必传**：与订单 `community_id` 一致，仅返回该小区已审核且档案 `active` 的技工 |
| `limit` | 条数上限，默认 200 |

响应 `data` 为数组，每项：

| 字段 | 说明 |
|------|------|
| `id` / `user_id` | 技工用户 ID（派单时传 `worker_id`） |
| `name` | 姓名 |
| `phone` / `industry` | 手机、行业 |
| `community_id` | 技工绑定小区 |

### 5.4 指派技工（到家）

**`POST /admin/service-orders/:id/assign`**（`:id` 为订单数字 id）

Body：

```json
{ "worker_id": 123 }
```

也可传 `worker_user_id`（与 `worker_id` 二选一逻辑以服务端为准）。

**业务条件（后端校验）**

- 订单 `status` 须为 **`paid_pending_dispatch`**，且 **`assigned_worker_id` 为空**
- 技工须已审核通过且档案 **`active`**
- 若订单带 **`community_id`**，技工 **`WorkerProfile.community_id` 须与订单一致**，否则返回失败（`errmsg` 含「小区」等说明）

成功：订单 **`status`** 更新为 **`dispatched`**，并写入 `assigned_worker_id`、`dispatch_at`、`dispatch_by`。

## 6. 技工端（小程序 / H5）

路由挂载：**`/api/v1/worker`**（具体以网关为准）。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/worker/service-orders` | 指派给当前技工的订单列表 |
| GET | `/worker/service-orders/:id` | 详情 |
| POST | `/worker/service-orders/:id/accept` | 接单（`pending_worker_accept` 或 `dispatched`） |
| POST | `/worker/service-orders/:id/reject` | 拒单，订单回流待派单/待支付等（见后端逻辑） |
| POST | `/worker/service-orders/:id/check-in` | 打卡 |
| POST | `/worker/service-orders/:id/evidence` | 上传前后凭证 |
| POST | `/worker/service-orders/:id/complete` | 完工 |

技工 JWT 与用户端均为业务用户登录体系，需使用 **技工账号** 登录后调用。

---

## 7. 服务商打包单（简要）

**`POST /service-orders/bundle`**：多 SKU / 服务商订单，支付成功后多为 **`pending_accept`**，履约走 **`/service-provider/...`** 系列接口，与九州「服务订单」派单队列不同；详情见 `doc/前端对接文档_服务商与技工系统.md`（若存在）。

---

## 8. 联调自检清单

| 步骤 | 用户端 | 预期 |
|------|--------|------|
| 1 | 分组页下单，不传 `worker_id` | `fulfillment_meta.dispatch_mode === admin_dispatch`（详情接口可见） |
| 2 | 支付成功 | `paid_pending_dispatch` |
| 3 | 管理端派单同小区技工 | `dispatched`，`assigned_worker` 有值 |
| 4 | `GET /service-orders/my` | 列表含该单，状态与详情一致 |
| 5 | 直约带 `worker_id` 支付后 | `pending_worker_accept`（直至技工接单） |

后端自测脚本（可参考）：`backend` 下 `npm run test:virtual-dispatch`。
